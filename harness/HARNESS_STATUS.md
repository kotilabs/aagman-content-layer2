- **India news scout (wired into main runner):** `harness_content/scouts/india_news_scout.py` runs the India-news signal prompt and writes `signals/<date>-india-news-digest.md`. - **Signal selection now supports multiple digest sources:** `python run_layer2_full.py select_signal` lists every digest that exists for the date (`combined`, `macro`, `india_news`, `x`, `reddit`) and asks you to pick a `digest_source` plus a `signal_id`. This lets you start the harness from any scout lens without cross-scout ranking or automatic merging.

- **Reddit Scout agent (wired into main runner):** `harness_agents/reddit_scout_agent.py` clusters posts from `r/IndianStockMarket`, `r/DalalStreetTalks`, `r/IndianStocks`, `r/IndianStreetBets`, and `r/MutualfundsIndia`. It is now callable directly from the Layer 2 orchestrator via `python run_layer2_full.py reddit_scout`. The cluster output is converted into a digest file (`signals/<date>-reddit-digest.md`) that `select_signal` can read alongside macro, India-news, and X digests. You can still run it standalone with `PYTHONPATH=. ./venv/bin/python harness_core/run.py --domain reddit_scout --once` or `reddit_cluster.py fetch --subreddits ... --date ...`. It sorts each subreddit by **hot** and **new**, fetches full post text, and clusters them by theme. A 20-second pause between subreddits was added to avoid rate-limit failures. The agent supports a direct OpenAI-compatible LLM path via `.env` keys `OPENAI_COMPATIBLE_API_KEY`, `OPENAI_COMPATIBLE_BASE_URL`, and `LLM_MODEL`; DeepSeek (`deepseek-chat`) is configured and tested. Provider order: `OPENAI_API_KEY` → `OPENAI_COMPATIBLE_API_KEY`+`OPENAI_COMPATIBLE_BASE_URL` → manual bridge fallback.

  **LLM evaluation notes for clustering:** Clustering is a good, cheap benchmark for model selection before using a model for long-form drafting. Key criteria, in order of importance: cluster quality (themes specific, posts actually belong together), noise handling (does the model over-use an "Other / Noise" bucket?), format adherence, ticker/theme recall, cost, availability from India, and latency. Current default is **DeepSeek `deepseek-chat`** — cheap, fast, reachable from India, but slightly aggressive on the "Other / Noise" bucket and occasionally verbose. Alternatives to test: **OpenAI `gpt-4o-mini`** (stronger instruction following, less over-noising, better ticker extraction, more expensive); **`gpt-4o`** (best quality, overkill cost); **Kimi/Moonshot** (non-US option, availability/pricing from India unclear); **local models** (privacy win, usually worse quality/speed). Suggested workflow: run the same raw post set through 2–3 models, score 1–5 on the criteria, track cost/latency, pick the cheapest model that produces clusters you trust, and re-evaluate quarterly. Open questions: whether DeepSeek v3 reduces over-noising; whether a two-stage prompt (extract tags → cluster) improves quality; whether to reassign borderline noise posts to existing clusters post-hoc.

- **X home-feed scout agent (wired into main runner):** `harness_agents/x_scout_agent.py` scrolls the logged-in user's X home feed via `browser-use` (same stack as Reddit), extracts ~60 tweets, uses an LLM to screen them for relevance to Indian finance/markets, expands the selected ones by opening their permalinks, and clusters the result. It is now callable directly from the Layer 2 orchestrator via `python run_layer2_full.py x_scout`, which converts clusters into a digest (`signals/<date>-x-digest.md`) readable by `select_signal`. You can still run it standalone with `PYTHONPATH=. ./venv/bin/python harness_core/run.py --domain x_scout --once` or `x_cluster.py fetch --date ...`. Requires the user to be logged in to X in the browser profile. No API cost, but dependent on browser session. Future work: consider shifting to an X MCP server (e.g., TwitterAPI.io or official X API) for a more durable, higher-throughput approach that can fetch more data without browser-session fragility; test selector robustness across X UI changes; add a manual relevance gate so the human picks which tweets to expand; evaluate whether expanding threads (vs. single tweets) improves cluster quality.

- **Posting layer strategy: SaaS now, Postiz later.** We are not waiting for Postiz to start publishing. The harness will publish through already-hosted SaaS platforms immediately, while Postiz is built and self-hosted on a VPS on the side. The blocker with Postiz is not just hosting — it is organizing and integrating APIs for every platform (LinkedIn, X, Substack, etc.), which is a long cross-platform process. The chosen interim SaaS is **Autoposting.ai**, which is MCP-native and exposes create/schedule/publish/list-brands tools over MCP, plus a REST API fallback at `https://app.autoposting.ai/api-proxy/`. The harness `PUBLISH` step will target an abstract `publisher` interface: it writes ready-to-publish artifacts to `outbox/` and, when API creds are available, calls Autoposting (MCP first, REST fallback) to schedule or post. Later, the same interface is swapped to Postiz with minimal code change. Analytics ingestion will similarly read from the SaaS platform's export/API until Postiz analytics are ready.

  **Config needed for Autoposting.ai:**
  - MCP endpoint + API key from `Autoposting.ai → Settings → API` (endpoint likely `https://app.autoposting.ai/mcp`).
  - API key scopes: `posts:write`, `posts:read`, `brands:read` minimum; add `carousels:write` if publishing carousels/infographics.
  - Brand ID / brand name the harness should post under.
  - Connected platforms for that brand (LinkedIn, X, etc.) already linked in the Autoposting dashboard.
  - Compatibility note: Autoposting MCP uses HTTP/SSE transport. If Kimi Code CLI cannot consume HTTP MCP directly, the harness will fall back to the Autoposting REST API with the same key.

  **Caveat — Autoposting.ai `delete-post` does not remove live platform posts (future work).** A live test on 2026-08-01 confirmed that `delete-post` removes the internal Autoposting record (the post disappears from `list-posts`), but the published content remains live on X and LinkedIn. For the harness this means: (a) treat Autoposting as publish + analytics-read, not as a way to retract content; (b) any automated experiment posts will remain visible on the brand's social feeds; (c) future work should integrate platform-native deletion APIs (X API, LinkedIn API) if true retraction is needed. Record this whenever designing the experiment/publish layer.

- **Analytics agent — wired and running against Buffer MCP.** The pipeline is now automated: `python run_layer2_full.py analytics --analytics-days 30` fetches metrics from Buffer, normalizes them, runs the `analytics_agent.md` prompt through the harness router, and writes the report to `layer2_full_run/analytics/<date>-analysis.md`. Implementation: `harness_content/analytics_agent.py`.

  - **Collection layer:** `BufferMCPClient` speaks JSON-RPC to `https://mcp.buffer.com/mcp`, calls `get_account`, `list_channels`, `list_posts(includeMetrics=true)`, and `get_aggregated_post_metrics`. It normalizes Buffer's per-service metrics (LinkedIn impressions/reactions/shares/comments; Instagram reach/views/reactions/shares/saves/follows) into a common schema. Optionally downloads each post's image/video assets to `layer2_full_run/analytics/assets/<date>/<post-id>/`.
  - **Substack CSV ingestion (field-agnostic):** Long-form Substack analytics are merged from a posts-export CSV. Set `SUBSTACK_CSV_PATH` in `.env` or pass `--substack-csv <path>` to `run_layer2_full.py analytics`. The collector only needs to locate a few metadata columns (`id`, `title`, `subtitle`, `published_at`, `text`/`body`, `url`); common aliases are auto-detected. **Every other numeric column in the CSV is ingested as a metric under its original name**, so different Substack exports with different data points all work without code changes. Common metric columns are also stored under canonical names (e.g., `email_deliveries`, `email_opens`, `likes`, `free_subscribers`) so the prompt can refer to them consistently.
  - Optional explicit mapping: if an export uses unusual metadata headers, provide `--substack-csv-mapping <json-file>` or set `SUBSTACK_CSV_MAPPING` in `.env`. The JSON file maps canonical field names to CSV column names, e.g. `{"title": "Post Title", "published_at": "Publish Date"}`. Substack posts appear alongside Buffer posts in the merged metrics JSON and in the analysis report.
  - **Visual-description layer:** `CreativeDescriber` downloads assets and can describe them via a vision model (`gpt-4o` through litellm). Enable with `--describe-assets`. If `OPENAI_API_KEY` is invalid/missing, the describer falls back to a type label and leaves the actual descriptions to be injected manually (see `layer2_full_run/analytics/enrich_descriptions.py` for the one-off manual-enrichment helper used on 2026-08-01).
  - **Analysis layer:** `AnalyticsAnalyzer` builds the prompt from `harness_content/prompts/analytics_agent.md`, injects aggregates + per-post metrics + `asset_descriptions` + historical averages per surface, and calls `router.complete("complex_planning", ...)`. It also recalls prior `content.publish` lessons from `AgentMemory` so the analyst does not contradict stored learnings.
  - **Conversational analytics:** `python run_layer2_full.py chat_analytics` opens a REPL over the latest metrics file. Ask natural-language questions like "which post had the highest impressions?", "compare linkedin vs instagram", or "what topics performed best?". It loads the normalized dataset, maintains conversation history, and routes each turn through the harness LLM router.
  - **Experiment layer:** Phase 1 is manual. The analysis report outputs a ranked experiment table; the operator logs chosen experiments to `experiments/` using the template, and the next analytics cycle matches results back to them. Phase 2 will add an autonomous experiment agent that reads the log, learns, designs the next variant, posts it, observes results, and writes lessons back to `AgentMemory`.

  **Config needed in `.env`:**
  - `BUFFER_MCP_TOKEN=<Buffer API token>` (required). Get it from `https://publish.buffer.com/settings/api`.
  - `BUFFER_MCP_ENDPOINT=https://mcp.buffer.com/mcp` (optional; defaults correctly).
  - `BUFFER_ORGANIZATION_ID=<org-id>` (optional; auto-detected from `get_account` if omitted).
  - `BUFFER_CHANNEL_IDS=id1,id2,id3` (optional; defaults to all connected channels).
  - `SUBSTACK_CSV_PATH=<path/to/substack_posts.csv>` (optional; merges Substack long-form analytics into the same report).
  - `SUBSTACK_CSV_MAPPING=<path/to/substack_mapping.json>` (optional; JSON mapping of canonical metadata fields to CSV column names).
  - `OPENAI_API_KEY=<valid OpenAI key>` (only if using `--describe-assets` for automated vision descriptions).

  **Buffer `delete_post` is verified to remove live platform posts.** Unlike Autoposting.ai, Buffer's `delete_post` retracts the content on the connected platforms as well. Treat Buffer as publish + analytics-read + retraction, with deletion verified as reliable.

  **First automated run (2026-08-01):** 10 posts across LinkedIn + Instagram (X had no posts in the 30-day window). All image assets were downloaded and manually described (automated vision was wired but the ambient `OPENAI_API_KEY` returned 401). The enriched descriptions let the analyst compare creative formats directly — e.g., "RBI reserves line chart" vs. "FPI/DII flow diagram" vs. "China property carousel". The analysis surfaced the same India-macro outlier pattern as the earlier CSV simulation — a single-image India-macro LinkedIn post reached 848 impressions (~23× the LinkedIn median). The report proposes five ranked experiments, starting with a link-in-body vs. link-in-comment test on LinkedIn.

  **Future work — image-assessment model.** The current `CreativeDescriber` uses `gpt-4o` for generic one-sentence captions. Longer term we should evaluate and possibly switch to a dedicated image-assessment model that can score creatives on dimensions relevant to the brand: chart readability, headline prominence, color consistency, data-to-noise ratio, carousel narrative flow, and predicted scroll-stopping power. Candidates to benchmark: OpenAI `gpt-4o`/o1 vision, Google Gemini 1.5 Pro/Flash vision, Anthropic Claude Sonnet vision, and open-source alternatives (LLaVA, Qwen-VL, InternVL) if cost or latency becomes an issue. The evaluation criteria should be: (1) accuracy of chart/infographic description, (2) ability to read specific numbers and labels, (3) consistency of scoring across similar posts, (4) cost per image, (5) latency, and (6) independence from a single provider. This is intentionally not built yet; start with a small held-out test set of 20–30 Aagman assets and score each model against human labels before wiring the winner into `analytics_agent.py`.

- **Experiment loop — Phase 1: manual log, Phase 2: autonomous agent.** For now, the analytics report produces a ranked experiment table; the operator selects which experiments to run and logs them to `experiments/` using `experiments/experiment_template.md` (hypothesis, variant A, variant B, surface, primary metric, minimum sample, effort, expected impact). The next analytics cycle can then match results back to the logged experiment manually. Phase 2 will add an autonomous experiment agent that reads the open experiment log, learns from it, designs the next post or variant, executes it via the publish layer, observes the result, and writes the learned lesson back to `AgentMemory` — closing the loop without operator handoff for every cycle.

- **Basic analytics observation → controlled experiment (in progress):** Early LinkedIn data from the company page (94 followers, 11 organic posts) is too thin to write durable lessons. One outlier stands out — a single-image infographic on the rupee–equity divergence reached 1,208 impressions, roughly 10× the median post. Carousels (China two-speeds, gold export) showed high engagement rates (13–17%) but low reach. Text-heavy posts with a Substack link preview performed weakest. However, the sample is heavily skewed toward global macro topics and mixed formats. Rather than storing these as lessons now, the next step is a 3–4 week controlled experiment: run India-market-focused content across single-image infographics, carousels, and short-copy posts, then compare format-vs-format and topic-vs-topic before writing approved patterns into `AgentMemory`. Substack remains too early to judge.

- **Experiment knowledge base.** Build a structured knowledge base of every experiment the harness has run — hypothesis, variants, surface, sample size, primary metric, result, confidence, and the lesson derived. This KB should be queried automatically before any new decision (signal selection, angle choice, format choice, publish timing) so the harness does not unknowingly repeat a failed variant or ignore a proven pattern. It should be distinct from the flat `AgentMemory` lesson store: queryable by surface + topic + format + metric, versioned, and capable of returning "no prior evidence" when appropriate.

- **Random writer agent.** Add a single-entry creative agent that takes a raw idea or brief and autonomously calls the right downstream agents in sequence — research, surface selection, writing, review, correction, SEO — to return a complete publish-ready package. The operator only supplies the idea; the agent decides which surfaces make sense, fans out the writers, runs the judge, applies corrections, and hands back final drafts for approval. This collapses the current multi-command workflow into one shot for rapid prototyping or ad-hoc content requests.

- **Chat with Analytics as a persistent, message-driven product.** The current `chat_analytics` command has been removed from the active analytics agent because the terminal REPL is unstable in non-TTY environments and the file-bridge one-shot mode still requires manual operator handoff. Future work is to reintroduce conversational analytics as a stateful session model: each conversation is persisted to a session file, the user sends a question as a message, the agent loads the latest metrics + conversation history, reasons, answers, and writes the updated context back. This enables multi-turn analytics Q&A across channels (this chat, Slack, email) without a live terminal. The agent should eventually be able to act on its answers too — e.g., after identifying a winning topic/format, it can draft a new post or schedule an experiment directly.
